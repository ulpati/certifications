## Understanding Virtual LAN (VLAN) Concepts

A **Local Area Network (LAN)** includes all devices within the same **broadcast domain** — meaning any broadcast frame sent by one device is received by all others in that domain.

By default, all switch interfaces belong to a single broadcast domain.  
However, by using **Virtual LANs (VLANs)**, a switch can divide a network into multiple broadcast domains, offering greater control and efficiency.

### Why Use VLANs?
Creating smaller broadcast domains provides several benefits:

- **Improved performance:** Reduces CPU overhead by limiting which devices receive broadcast traffic.  
- **Enhanced security:** Restricts the number of hosts exposed to broadcast and flooded traffic.  
- **Policy flexibility:** Allows applying different security and access policies per VLAN.  
- **Logical grouping:** Users can be grouped by department or function rather than physical location.  
- **Simplified troubleshooting:** Failures are confined within the same broadcast domain.  
- **Efficient STP operation:** Limits each VLAN to specific access switches, reducing Spanning Tree workload.

## Creating Multi-Switch VLANs with Trunking

When multiple switches are interconnected, **VLAN trunking** allows them to carry traffic for multiple VLANs across a single physical link.  
This is achieved by adding a **VLAN tag** to Ethernet frames — a process known as **VLAN tagging** — which includes a **VLAN Identifier (VLAN ID)** to distinguish traffic between VLANs.

Without trunking, a separate physical link would be required for each VLAN, which is not scalable.

---

### VLAN Trunking Protocols: 802.1Q and ISL

Cisco switches have historically supported two trunking protocols:  
- **Inter-Switch Link (ISL)** – Cisco proprietary.  
- **IEEE 802.1Q** – The industry standard and most commonly used today.

**802.1Q** inserts a 4-byte VLAN header into the Ethernet frame.  
- The **VLAN ID** field is **12 bits**, supporting up to **4096 VLANs** (IDs 0 and 4095 are reserved, leaving 1–4094 usable).  
- VLANs 1–1005 are considered **normal range**, while 1006–4094 are **extended range**, supported depending on the **VTP configuration mode**.

#### The Native VLAN
802.1Q defines a **native VLAN** (default: VLAN 1).  
Frames belonging to the native VLAN are **not tagged** on trunk links.  
Both ends of a trunk must agree on the same native VLAN to ensure consistency.

If a trunking device connects to a non-trunking one, untagged frames (native VLAN traffic) are still understood by the non-trunking device, preventing communication failures.

## Forwarding Data Between VLANs

Layer 2 switches **cannot forward traffic between VLANs**.  
Since each VLAN represents a separate subnet, inter-VLAN communication requires a **router or Layer 3 switch**.

### Routing Between VLANs
When using a router with a Layer 2 switch:
- A host in VLAN A sends packets to its **default gateway** (the router).  
- The router forwards the packets out through another interface assigned to **VLAN B**.  
- Each VLAN remains a distinct broadcast domain and IP subnet.

This process is often called **“router-on-a-stick”** when a single physical link is trunked to handle multiple VLANs.

## VLAN and Trunking Configuration and Verification

### Creating VLANs and Assigning Access VLANs

To create a VLAN:
```
configure terminal
vlan <vlan_id>
name <name>     # Optional
```

If no name is set, the default format is VLANX (e.g., VLAN10).

To assign interfaces to a VLAN:
```
interface <type_number>
switchport access vlan <vlan_id>
switchport mode access   # Optional: ensures access-only mode
```

---

### VLAN Trunking Protocol (VTP)

**VTP (VLAN Trunking Protocol)** automatically advertises VLAN information between Cisco switches, synchronizing configurations across the network.

- Disable VTP: `vtp mode transparent` or `vtp mode off`
- Verify status: `show vtp status`

CCNA exams no longer cover VTP in depth, so only basic awareness is needed.

---

### VLAN Trunking Configuration

To define trunk encapsulation: `switchport trunk encapsulation <dot1q | isl | negotiate>`

**Trunk Mode Options**
| Command Option      | Description                                              |
| ------------------- | -------------------------------------------------------- |
| `access`            | Always operate as an access (non-trunk) port             |
| `trunk`             | Always operate as a trunk port                           |
| `dynamic desirable` | Actively tries to negotiate trunking                     |
| `dynamic auto`      | Passively waits for the other side to negotiate trunking |

**Operational Mode Matrix**
| Local \ Remote        | Access  | Dynamic Auto | Trunk   | Dynamic Desirable |
| --------------------- | ------- | ------------ | ------- | ----------------- |
| **Access**            | Access  | Access       | Avoid | Access            |
| **Dynamic Auto**      | Access  | Access       | Trunk   | Trunk             |
| **Trunk**             | Avoid | Trunk        | Trunk   | Trunk             |
| **Dynamic Desirable** | Access  | Trunk        | Trunk   | Trunk             |

⚠️ Avoid connecting an access port to a trunk port — this causes communication issues.
Cisco recommends disabling Dynamic Trunking Protocol (DTP) on most ports for better security using:
```
switchport mode access
switchport nonegotiate
```

### Implementing Interfaces Connected to Phones
IP Phones use Ethernet to connect both voice and data devices.
To separate voice and data traffic efficiently, Cisco switches support **Voice VLANs**.

This configuration allows:

- One VLAN for **voice traffic** (to prioritize and manage QoS).
- Another VLAN for **data traffic** (for the user’s PC).

Example:
```
interface <interface_id>
switchport mode access
switchport access vlan <data_vlan>
switchport voice vlan <voice_vlan>
```

## Troubleahooting VLANs and VLAN Trunks

### Verifying Access VLAN Assignments

| Command                            | Description                                                    |
| ---------------------------------- | -------------------------------------------------------------- |
| `show vlan brief`                  | Lists VLANs and their assigned interfaces (not trunks)         |
| `show vlan id <num>`               | Shows both access and trunk ports for a specific VLAN          |
| `show interfaces status`           | Displays interface status, including VLAN membership for access ports and “trunk” for trunk ports |
| `show interfaces <int> switchport` | Shows access VLAN, voice VLAN, and operational mode            |
| `show mac address-table`           | Displays learned MAC addresses and their VLAN associations     |


---

### Undefined or Disabled VLANs

Switches do **not forward** traffic for VLANs that are:

- **Not configured** locally or learned via VTP.
- **Disabled** using administrative commands.

To disable/enable VLANs:
```
shutdown vlan <vlan_id>
no shutdown vlan <vlan_id>
```

or in VLAN mode:
```
shutdown
no shutdown
```

---

### Trunking State Mismatches
Common issues include:
- Both ends set to `switchport mode dynamic auto`, resulting in **no trunk**.
- One end trunking while the other operates in **access mode**.

In such cases:

- The link appears **up/up**, but only native VLAN traffic (untagged) passes.
- Other VLANs fail to communicate.

Key troubleshooting commands:
```
show interfaces trunk
show interfaces switchport
```

---

### Supported VLAN List on Trunks
To check which VLANs are allowed on a trunk: `show interfaces <interface_id> trunk`

A VLAN will appear in the list if:

- It’s **allowed** on the trunk (`switchport trunk allowed vlan` command).
- It’s **active** and exists locally.
- It’s **not pruned** by VTP.
- The port is in a **Spanning Tree forwarding state**.

To limit VLANs on a trunk: `switchport trunk allowed vlan <range>`

---

### Mismatched Native VLANs

To configure or correct the native VLAN: `switchport trunk native vlan <vlan_id>`

If two switches use **different native VLANs**, untagged traffic can “hop” between VLANs, creating a **security risk (VLAN hopping)**.
