## Understanding Named ACLs and ACL Editing

### What Are Named IP Access Lists?

Named Access Control Lists (ACLs) were introduced to make ACL management easier and more flexible compared to numbered ACLs.  
They differ from traditional numbered ACLs in three main ways:

1. **Human-readable names:** ACLs are identified by descriptive names instead of numeric IDs, making it easier to remember their purpose.  
2. **Configuration mode:** Named ACLs use a specific *ACL configuration mode* (entered via subcommands) rather than global configuration commands.  
3. **Editing capabilities:** They allow administrators to insert, delete, or modify individual Access Control Entries (ACEs) without re-creating the entire list.

To create a named ACL, use:

```

ip access-list <standard | extended> <name>

```

Once inside ACL configuration mode, you can define rules using commands like:

```

permit <address> <wildcard_mask>
deny <address> <wildcard_mask>
remark <text comment>

```

The `remark` keyword is useful for adding documentation or notes to the ACL.

#### Rules for ACL Names
- Names must begin with a **letter**.  
- **Spaces** and **quotation marks** are **not allowed**.  
- Names are **case-sensitive**.

When a named ACL is created, IOS automatically assigns sequence numbers to its entries, starting at **10** and incrementing by **10** for each new ACE.

## Editing ACLs in Cisco IOS

### Editing Named ACLs

To modify a named ACL, enter its configuration mode:

```

ip access-list <standard | extended> <name>

````

From there, you can:

- **Delete a specific ACE**  
  - Re-enter the same permit/deny command preceded by `no`, *or*  
  - Use `no <sequence_number>` to remove the entry directly.

> Example:
> ```
> no 20
> ```
> This deletes the ACE with sequence number 20.

Deleting entries doesn’t affect the numbering of the remaining ACEs.  
You can also **insert new ACEs** in specific positions by using sequence numbers:

````

10 permit 192.168.1.0 0.0.0.255
15 deny 10.0.0.0 0.255.255.255

````

If you omit a sequence number, IOS automatically appends the new ACE to the **end** of the ACL.

---

### Editing Numbered ACLs

Traditional numbered ACLs are more restrictive:

- You **cannot** delete individual ACEs.  
- Using `no access-list <number>` removes the **entire ACL**.  
- You can only **append** new ACEs to the end of the list.

However, in modern IOS versions, numbered ACLs can also be edited using the ACL configuration mode, providing more flexibility similar to named ACLs.

> **Recommendation:**  
> Before editing any ACL, Cisco advises temporarily **removing it from the interface** using `no ip access-group`, performing the edits, and then **re-applying** it afterward.

## Extended IP Access Control Lists (Extended ACLs)

Extended ACLs work like standard ACLs but offer **finer control** by allowing multiple packet fields to be matched within a single ACE.  
Each ACE can filter based on the **protocol**, **source IP**, **destination IP**, and even **TCP/UDP port numbers**.

---

### Matching Protocol, Source, and Destination IP

Extended ACLs are identified by number ranges:
- **100–199** (standard range)
- **2000–2699** (expanded range)

To match the protocol type, use keywords such as:

- `ip` — all IPv4 traffic  
- `tcp` — Transmission Control Protocol  
- `udp` — User Datagram Protocol  
- `icmp` — Internet Control Message Protocol  

> **Example:**
> ```
> access-list 101 permit tcp 192.168.1.0 0.0.0.255 any
> ```

In extended ACLs, **all conditions** within an ACE must match for the packet to be considered a match.  
Only two addressing formats are supported:
- `<ip_address> <wildcard_mask>`  
- `host <ip_address>`  

Simply specifying an IP address without a mask or `host` keyword is invalid.

---

### Matching TCP and UDP Port Numbers

Extended ACLs can filter packets based on **source** and **destination port numbers**.  
This allows precise control over application-level traffic.

You can specify comparisons such as:
- `eq` (equal to)
- `ne` (not equal)
- `lt` (less than)
- `gt` (greater than)
- `range` (between two port numbers)

Ports can be written numerically or using **well-known keywords**, such as:

| Keyword | Port | Application |
|----------|------|-------------|
| `www` | 80 | HTTP |
| `ftp` | 21 | FTP |
| `ssh` | 22 | SSH |
| `dns` | 53 | DNS |
| `https` | 443 | HTTPS |

> **Example:**
> ```
> access-list 101 permit tcp any any eq www
> ```

This command allows HTTP traffic (port 80) from any source to any destination.

---

### Configuring Extended IP ACLs

The configuration workflow for extended ACLs is similar to standard ACLs, with a few key differences:

1. **Placement:**  
   - Place extended ACLs **close to the source** of the traffic being filtered.  
     This approach conserves bandwidth by blocking unwanted traffic early.

2. **Match Logic:**  
   - All fields in a single ACE must match for the rule to apply.

3. **Number Range:**  
   - Use numbers **100–199** or **2000–2699** for extended ACLs.

> **Example:**
> ```
> access-list 110 deny tcp any 10.0.0.0 0.255.255.255 eq 23
> access-list 110 permit ip any any
> ```

This ACL blocks Telnet (port 23) traffic to the 10.0.0.0/8 network but permits everything else.

---

## ACL Design and Implementation Best Practices

Cisco recommends the following strategies for designing effective ACLs:

- **Extended ACLs:** Place as close as possible to the **source** of unwanted traffic.  
- **Standard ACLs:** Place as close as possible to the **destination** to prevent accidental packet drops.  
- **Order of entries:** Put more **specific rules first**, followed by more **general** ones.  
- **Editing:** Temporarily **remove ACLs from interfaces** before editing.  
- **Verification:** Ensure that the correct ACL is applied with the intended name or number (case-sensitive for named ACLs).
