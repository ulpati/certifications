## Introduction to IPv4 Access Control Lists

**IPv4 Access Control Lists (ACLs)** are tools that allow network engineers to identify and control the flow of packets through a network.  
By defining specific rules based on information found in IP, TCP, UDP, or other headers, ACLs can determine which packets are allowed or denied as they traverse a router.  

Their most common use is as a **packet filter**—deciding which traffic can pass through and which should be blocked.

---

## ACL Location and Direction

An ACL can be applied in two directions relative to a router’s interface:

- **Inbound:** Filters packets **before** the router makes a routing decision.  
- **Outbound:** Filters packets **after** the router decides which interface to send them out from.

To configure filtering properly, identify both the inbound and outbound interfaces that a packet uses as it moves through the router.  
Multilayer switches that route IP packets use the same ACL principles.

---

## Matching Packets

"Matching packets" refers to how ACLs identify which packets should be allowed or denied.  
Each ACL is made up of one or more **Access Control Entries (ACEs)**—individual rules that define conditions based on header information, such as:

- Source IP address  
- Destination IP address  
- TCP or UDP port numbers  

When a packet matches one of these ACEs, the router performs the action specified in that line.

---

## Actions When a Match Occurs

For each matching packet, the ACL can perform only one of two actions:
- **permit** – allow the packet to continue
- **deny** – discard the packet

If a packet does not match any rule, it is automatically denied due to the **implicit “deny any”** rule at the end of every ACL.

---

## Types of IPv4 ACLs

IPv4 ACLs can be categorized as follows:

- **Standard numbered ACLs:** 1–99  
- **Extended numbered ACLs:** 100–199  
- **Expanded standard ACLs:** 1300–1999  
- **Expanded extended ACLs:** 2000–2699  
- **Named ACLs:** ACLs identified by a name instead of a number  

> **Note:** Standard ACLs filter traffic only based on the **source IP address**.

---

## Standard Numbered IPv4 ACLs

### ACL List Logic

Cisco IOS ACLs use **first-match logic**—once a packet matches one ACE, the router performs the associated action and stops checking further entries.  
If a packet does not match any ACE, it is implicitly denied.  
This logic applies to all ACL types: IPv4, IPv6, numbered, named, standard, or extended.

---

### Matching Logic and Syntax

The general command format for a standard numbered ACL is:

```

access-list <1-99 | 1300-1999> <permit | deny> matching-parameters

```

Each ACE uses specific parameters to define what traffic it matches.

---

### Matching an Exact IP Address

To match a single host or exact IP address:

```

access-list <1-99 | 1300-1999> permit <ip_address>
access-list <1-99 | 1300-1999> permit host <ip_address>
access-list <1-99 | 1300-1999> permit <ip_address> <wildcard_mask>

```

Even though multiple formats exist, IOS normalizes and stores them in a consistent structure.

---

### Matching Subnets with Wildcard Masks

A **wildcard mask** lets ACLs match a range of IP addresses instead of a single host.

| Decimal Value | Behavior |
|----------------|-----------|
| **0** | Router must compare this octet exactly. |
| **255** | Router ignores this octet (it automatically matches). |

**Example:**  
A wildcard mask of `0.0.0.255` means the last octet is ignored, matching any host within that subnet.

---

### Binary Wildcard Masks Explained

To understand wildcard mask logic:

1. Convert the IP address from the ACL and the packet’s source IP to binary.  
2. Convert the wildcard mask to binary.  
3. For each bit:
   - If the wildcard bit is **1**, ignore that position.
   - If the wildcard bit is **0**, compare the corresponding bits in both addresses.

If all compared bits match, the ACL line matches that packet.

---

### Finding the Correct Wildcard Mask for a Subnet

A quick way to derive the wildcard mask for a subnet is:

```

Wildcard Mask = 255.255.255.255 - Subnet Mask

```

**Example:**  
For a subnet mask of `255.255.255.0`, the wildcard mask is `0.0.0.255`.

---

### Matching Any or All Addresses

To match **all traffic**, use:

```

access-list <1-99 | 1300-1999> permit any

````

This is useful when you want to allow all packets after applying other specific deny rules.

## Implementing Standard IP ACLs

Follow these steps when configuring a standard ACL:

1. **Plan the location and direction.**
   - Standard ACLs should be placed **near the destination** of the traffic to avoid blocking unintended packets.
   - Since they only match on **source IP**, choose an interface and direction that ensures the correct traffic is evaluated.

2. **Create the ACL.**
   - Use one or more `access-list` commands to define rules.
   - Remember that ACLs use **first-match logic**.
   - Any unmatched packet will be **implicitly denied**.

3. **Apply the ACL to an interface.**
   - Use:
     ```
     ip access-group <acl-number> in | out
     ```
   - This command applies the ACL to inbound or outbound traffic on a specific interface.

> The `ip access-group` command works only on interfaces that are enabled for IP routing.

## Troubleshooting and Verification

Useful commands for ACL management:

| Command | Description |
|----------|--------------|
| `show ip access-lists` | Displays IPv4 ACLs only. |
| `show access-lists` | Lists all configured ACLs (any protocol). |
| `clear ip access-list counters` | Resets the packet match counters for ACL entries. |

**Important note:**  
Routers treat **self-generated packets** (e.g., routing updates, local pings, traceroutes) differently from forwarded packets.  
Outbound ACLs are **not applied** to packets generated by the router itself.

To log ACL activity, add the `log` keyword to an ACL line:

````

access-list 10 deny 192.168.1.0 0.0.0.255 log

```

This causes IOS to periodically output messages about matching packets.
