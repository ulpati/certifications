## ACLs and Network Infrastructure Protocols

Access Control Lists (ACLs) can do much more than just filter user data traffic — they can also control or permit essential network protocols such as DNS, ICMP, DHCP, and routing protocols. Understanding how to properly filter or allow these protocols is crucial for maintaining both security and network functionality.

---

### Filtering DNS Traffic

DNS is one of the most fundamental services in any network. It typically uses both **UDP** and **TCP** on **port 53** (represented in ACLs with the keyword `domain`).  
Since DNS requests and responses traverse nearly every router in a corporate network, ACLs should always **allow DNS traffic** unless there’s a specific reason to block it.

---

### Filtering ICMP

The `ping` command relies on **ICMP Echo Request** messages, while the target device responds with **ICMP Echo Reply** messages.  
When designing ACLs, ICMP filtering can range from permissive to very restrictive depending on the desired policy.

Here are three common approaches:

1. **Simple (One-Stage) Approach:**  
   Allow all ICMP messages.

2. **Moderate (Two-Stage) Approach:**  
   - Allow ICMP messages where both source and destination are within the internal network.  
   - Deny all other ICMP traffic.

3. **Restrictive Approach:**  
   - Allow only ICMP `echo` and `echo-reply` messages between internal hosts.  
   - Deny all other ICMP types.

> **Note:**  
> ICMP messages such as *Time Exceeded* (used by `traceroute`) will be blocked under the last approach, preventing traceroute from working properly.

In ACL syntax, ICMP traffic is matched using the keyword `icmp` (not `tcp` or `udp`).

---

### Filtering OSPF

While ACLs **can** block OSPF messages, doing so serves little practical purpose.  
Routers typically **bypass outbound ACLs** for packets they generate locally — including routing protocol messages like OSPF.

> **IOS XE Note:**  
> In IOS XE, you can change this default behavior with the global command:
> ```
> ip access-list match-local-packets
> ```
> If using this option, the `ospf` protocol keyword can be used in ACLs.

---

### Filtering DHCP

DHCP traffic uses UDP ports **67** (server) and **68** (client).  
There are two main approaches to handling DHCP in ACLs:

1. **One-Stage Approach:**  
   Permit all DHCP traffic destined for the DHCP server (`udp eq bootps`).

2. **Two-Stage Approach:**  
   - Allow DHCP packets only to **authorized servers**.  
   - Deny all other DHCP messages directed to potential rogue servers.

> **Note on Helper Addresses:**  
> - When a router uses the `ip helper-address` command, any packets modified by that function **bypass outbound ACLs** by default.  
> - If both an inbound ACL and a helper function exist on the same interface, the ACL check occurs **before** the helper function modifies the DHCP packet.

---

### Filtering SSH and Telnet

#### For End Users

Both SSH and Telnet use **TCP**, with **ports 22 and 23**, respectively (Telnet can also be referenced by the keyword `telnet` in ACLs).

Two main scenarios are common:

1. **One-Stage Approach:**  
   Permit all SSH and Telnet connections to internal servers.

2. **Two-Stage Approach:**  
   - Allow SSH and Telnet connections between trusted internal hosts.  
   - Deny all other such connections.

---

#### For Router VTY (CLI) Access

To protect access to router command-line interfaces, Cisco IOS provides **vty ACLs**, configured with the `access-class` command under **vty line configuration mode**.

When a user connects to a router using SSH or Telnet, IOS associates that session with a vty line. ACLs can then control which IP addresses are allowed to establish those sessions.

Key rules for vty ACLs:
- They apply only to traffic **destined for the router’s own IP interfaces**.  
- Only packets targeting **SSH or Telnet ports** are considered.  
- Typically, a **standard ACL** is sufficient, matching only the source IP addresses of clients.

To enable vty ACLs:

````

access-class <acl_name> in

```

The keyword `in` filters **incoming** SSH/Telnet connections.  
To filter **outgoing** sessions (initiated by the router), use `out` instead.

## Comparing ACLs in Cisco IOS vs. IOS XE

While Cisco IOS and IOS XE share the same overall ACL logic, they differ in several configuration and operational aspects. The following table summarizes key distinctions:

| **Feature** | **IOS** | **IOS XE** |
|--------------|----------|-------------|
| Supports numbered ACLs with global configuration commands | ✅ Yes | ✅ Yes |
| Supports numbered ACLs with ACL mode commands | ✅ Yes | ✅ Yes |
| Displays numbered ACLs as global commands in `running-config` | ✅ Yes | ❌ No |
| Named ACLs use ACL mode syntax | ✅ Yes | ✅ Yes |
| `show running-config` lists sequence numbers | ❌ No | ✅ Yes |
| `show access-lists` lists sequence numbers | ✅ Yes | ✅ Yes |
| Resequences ACL entries automatically on reload | ✅ Yes | ❌ No |
| Allows a second (common) ACL per interface/direction | ❌ No | ✅ Yes |
| Matches multiple nonconsecutive ports with `eq` | ❌ No | ✅ Yes |

> **Note:**  
> - In IOS, ACLs are stored as **global commands**, while IOS XE stores them as **ACL mode commands** regardless of how they were configured.  
> - IOS XE's **ACL persistence** feature keeps ACL numbering consistent across reloads unless explicitly disabled.

---

### Resequencing ACL Sequence Numbers

IOS automatically **reassigns ACL sequence numbers** after every reload, numbering entries as 10, 20, 30, and so on.  
Both IOS and IOS XE allow **manual resequencing** with the command:

```

ip access-list resequence <name|number> <starting_number> <increment>

```

In IOS XE:
- **Automatic resequencing** does *not* occur by default.
- The behavior is controlled by:
```

ip access-list persistent

```
(enabled by default).  
- To mimic IOS behavior, disable persistence using:
```

no ip access-list persistent

```

---

### Using a Second (Common) Interface ACL

Traditionally, Cisco routers allow **one ACL per protocol, per direction, per interface**.  
That means you cannot apply multiple ACLs in sequence on the same interface.

IOS XE, however, introduces support for a **second ACL**, known as a **common ACL**, alongside the standard one.  
Packets are processed by the **common ACL first**, followed by the **regular ACL**.

To configure this, use the standard command with the `common` keyword:

```

ip access-group <acl_name> in common

```

---

### Matching Multiple Nonconsecutive Ports with `eq`

In Cisco IOS, each nonconsecutive port must be matched by a separate ACE.  
For example:

```

permit tcp any any eq 20
permit tcp any any eq 21

```

IOS XE enhances this by allowing up to **ten ports** to be specified in a **single ACE**:

```

permit tcp any any eq 10 20 30 40 50 60

```

This feature simplifies ACL configuration and reduces complexity in access lists.
