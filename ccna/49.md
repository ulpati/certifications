## Server Virtualization

In most CCNA contexts, a *server* is simply a platform that runs applications, with users connecting to those applications over a network.

### Cisco Server Hardware

Modern servers differ significantly from traditional desktop systems. Key characteristics include:

- **No permanent KVM**: Servers typically operate without a fixed keyboard, monitor, or mouse. Administrators and users access them remotely through the network, eliminating the need for physical peripherals.
- **High-density data center design**: Servers are installed in racks within data centers, allowing many hosts to occupy minimal space. Their form factors follow standard rack dimensions, improving efficiency and simplifying physical organization.

Regardless of the hardware layout, servers provide CPU resources, memory, storage, and network interfaces. The major shift today is not just in hardware—it’s how the operating system (OS) is used through virtualization.

---

## Server Virtualization and Virtual Machines

Traditionally, one physical server ran one OS, and that OS ran the applications. Virtualization changes this model entirely. Instead of tightly coupling an OS to a single server:

- The data center treats all physical hardware as a shared resource pool.
- Each OS operates as a **virtual machine (VM)**—a self-contained environment independent of the underlying hardware.
- A single physical server often hosts multiple VMs because modern hardware provides more processing power than a single OS usually needs.
- A **hypervisor** manages this process, allocating CPU threads (exposed as **vCPUs**), RAM, storage, and virtual NICs (vNICs) to each VM.

Each VM works as if it had its own dedicated physical server, even though it shares resources with many others.

---

## Networking with Virtual Switches

Each VM includes one or more virtual network interface cards. To interconnect these vNICs with the server’s physical interfaces, the hypervisor uses a **virtual switch (vSwitch)**.

A vSwitch supports capabilities similar to a physical Ethernet switch:

- **Ports for VMs**: Each VM can be placed in its own VLAN, share VLANs with other VMs, or even use trunking.
- **Ports for physical NICs**: vSwitch uplinks typically use VLAN trunking to connect to the physical network.
- **Automated configuration**: Virtualization platforms dynamically configure vSwitches, especially when moving VMs between hosts.

---

## Software Containers

Containers aim for the same goal as VMs—isolating applications—but do so more efficiently. Compared to VMs, containers:

- Use fewer CPU and memory resources.
- Start and stop much faster.
- Contain the application and all its dependencies (except the OS), packaged in a **container image**.

A **container engine**—such as Docker—runs containers, manages their lifecycle, and provides remote management APIs. Containers launch in seconds, making them well-suited for scalable and automated environments. Tools like Kubernetes and Terraform orchestrate large deployments.

---

## The Physical Data Center Network

A typical virtualized data center links servers to two **Top of Rack (ToR)** switches for redundancy. These feed into **End of Row (EoR)** distribution switches, forming a scalable and resilient architecture connecting all hosts.

---

## Virtualized Data Center Workflow

Virtualization improves data center operations but does not necessarily create a cloud environment by itself. Here’s how typical VM provisioning works:

1. A customer (developer, operations staff, or another internal team) requests new services, such as VMs.
2. Virtualization engineers fulfill the request—manually or via automation scripts.
3. The virtualization platform deploys and configures multiple VMs across available servers.

Key capabilities that enable cloud operations:

- OS instances (VMs or containers) are independent from physical hardware.
- Virtualization software can migrate workloads across servers automatically.
- Networking is virtualized and configurable programmatically.
- VMs/containers can be started, moved, configured, or stopped with automated tools.

# Cloud Computing Services

Cloud services support both VMs and containers. For simplicity, this section focuses on VMs.

### Core Cloud Characteristics (Based on NIST)

Cloud computing provides:

- **On-demand self-service**: Consumers start and stop resources without provider intervention.
- **Broad network access**: Resources are reachable through many devices and networks.
- **Resource pooling**: Providers allocate resources dynamically from a shared pool.
- **Rapid elasticity**: Capacity scales quickly to meet demand.
- **Measured service**: Usage is monitored and used for billing and reporting.

---

## Private Cloud (On-Premise)

A private cloud provides cloud-like services inside a company. The organization:

- Owns and operates the cloud environment.
- Implements automation, service catalogs, and virtualized resource pools.
- Delivers services that meet NIST cloud criteria.

The term *on-premise cloud* refers to this internal, company-controlled architecture.

---

## Public Cloud

Public cloud providers deliver services to external customers. Users request resources via a service catalog, and the cloud platform provisions them in remote data centers. Similar tools and workflows exist as in private cloud, but ownership lies with a third-party provider.

---

## The “As a Service” Model

Cloud computing delivers services rather than specific hardware or software.

### Infrastructure as a Service (IaaS)

- Consumers choose VM specs (CPU, RAM, storage).
- Providers “spin up” the VM and supply access.
- Users configure the OS and software as needed.

### Software as a Service (SaaS)

- Users access a fully functional application.
- Providers manage the underlying VMs, containers, and software.
- No installation or maintenance is required by the consumer.

### Platform as a Service (PaaS)

- A prebuilt development environment delivered as a service.
- Includes OS plus development frameworks, libraries, and tools.
- Ideal for software development workflows.

---

## Virtual Routing and Forwarding (VRF)

When multiple customers share the same cloud infrastructure, overlapping IP subnets become common. VRF solves this by creating multiple independent routing tables within one router:

- Each VRF has its own interfaces and routing protocols.
- Routes remain isolated, preventing conflicts.
- The original table remains as the **global routing table**.

VRFs allow different customers to use the same IP ranges without interference.

# WAN Connectivity for Cloud Services

## Connecting an Enterprise to Public Cloud

### Using the Internet

Enterprise teams access cloud service catalogs over the Internet. After deploying cloud VMs or applications, users and other internal systems must communicate with these cloud-hosted services.

#### Pros of Internet Connectivity

- Quick setup
- Easier migration between cloud providers
- Works naturally with remote workers

#### Cons

- Less secure without a VPN
- Requires careful bandwidth planning
- No Quality of Service (QoS)
- No guaranteed performance SLA

---

### VPN Over the Internet

Adding a VPN improves privacy but still lacks QoS because it relies on the public Internet.

---

### MPLS VPN or Ethernet WAN

Enterprises can build private connections to cloud providers. This offers:

**Pros**

- Strong security  
- QoS support  
- Predictable performance  

**Cons**

- Slower provisioning  
- Higher cost  
- Harder migration to another cloud provider  

---

### Intercloud Exchanges

An **intercloud exchange** connects enterprises to multiple cloud providers through one private WAN platform. Benefits include simplified migration but add another company to the architecture.

---

### Summary of WAN Options

|                      | Internet | Internet VPN | MPLS VPN | Ethernet WAN | Intercloud Exchange |
|----------------------|----------|--------------|----------|--------------|----------------------|
| Makes data private   | No       | Yes          | Yes      | Yes          | Yes                  |
| Supports QoS         | No       | No           | Yes      | Yes          | Yes                  |
| Requires planning    | Yes      | Yes          | Yes      | Yes          | Yes                  |
| Eases migration      | Yes      | Yes          | No       | No           | Yes                  |
| Fast installation    | Yes      | Yes          | No       | No           | No                   |

# Cloud Management

Cloud management tools offer several advantages over traditional device-by-device management:

- **Centralized administration** for distributed networks
- **Remote accessibility** from anywhere
- **Scalable infrastructure** with elastic resource allocation
- **Automation** for provisioning, configuration, and troubleshooting
- **Enhanced security** with built-in controls
- **Lower operational costs** by reducing on-premises hardware needs

### Cloud vs Traditional Management

| Use Case | Cloud Management | Traditional Management |
|----------|------------------|------------------------|
| Centralized control | Central dashboard | Device-by-device unless using NMS |
| Deployment speed | Zero-touch provisioning | Often manual or scripted |
| Security policies | Applied centrally | Often configured per device |
| Troubleshooting | Holistic network view | Time-consuming, per-device |
| Monitoring/reporting | Unified cloud interface | Typically via third-party tools |
