## Understanding RSTP Configuration

### The Need for Multiple Spanning Trees

In networks with multiple VLANs, maintaining separate spanning tree instances helps isolate traffic and enhance performance. Cisco switches support several STP modes to accommodate different designs and standards.

---

### STP Modes and Standards

Cisco switches can operate in one of three spanning tree modes:

- **PVST+ (Per VLAN Spanning Tree Plus):** Classic STP-based mode with one instance per VLAN.  
- **RPVST+ (Rapid PVST+):** RSTP-based version providing faster convergence per VLAN.  
- **MSTP (Multiple Spanning Tree Protocol):** IEEE 802.1s standard allowing multiple VLANs to share a single spanning tree instance.

To select the desired mode: `spanning-tree mode <pvst | rapid-pvst | mst>`

---

### Bridge ID and System ID Extension

Each switch is uniquely identified by its **Bridge ID (BID)**, which consists of:
- **4-bit priority field**
- **12-bit system ID extension (VLAN ID)**
- **48-bit MAC address**

Cisco allows modification of only the priority portion using: `spanning-tree vlan <vlan-id> priority <value>`

The priority must be a multiple of 4096.
The default BID priority is **32768**.

---

### Identifying Switch Priority and the Root Switch

To verify which switch is the **root bridge**, use: `show spanning-tree vlan <vlan-id>`

The output displays the Root ID (current root switch) and local switch details.

#### Root Primary and Secondary Configuration

You can configure preferred root switches:
```
spanning-tree vlan <vlan-id> root primary
spanning-tree vlan <vlan-id> root secondary
```

These commands automatically adjust switch priority values to make the devices the most likely root candidates.

---

### Viewing Port Cost, Role, and State
To examine interface roles and costs: `show spanning-tree vlan <vlan-id>`

This command displays each interface’s **port cost**, **role**, and **state**.

Modify interface STP cost as follows:
- For a specific VLAN: `spanning-tree vlan <vlan-id> cost <value>`
- For all VLANs: `spanning-tree cost <value>`

## Configuring Optional STP Features

### PortFast and BPDU Guard

#### PortFast and BPDU Guard on Access Ports

PortFast allows an interface to transition immediately to the forwarding state, bypassing normal STP timers. It’s typically used on access ports connected to end devices: `spanning-tree portfast`

To prevent misconfigurations where a user connects another switch to a PortFast-enabled port, enable **BPDU Guard** (Bridge Protocol Data Unit Guard):
```
spanning-tree bpduguard enable
spanning-tree bpduguard disable
```

- **Trigger**: A BPDU is received on a PortFast-enabled port.
- **Action**: The port is placed in the err-disabled state.
- **Recovery**: Manually reset the interface with `shutdown` followed by `no shutdown`.

---

#### PortFast on VLAN Trunks and Voice Ports

PortFast can also be enabled on trunk ports that connect to **end devices** (e.g., IP phones), not to other switches: `spanning-tree portfast trunk`

When verifying:
- **P2p Edge** indicates PortFast is active.
- **P2p** means the port operates normally without PortFast.

---

#### Global Configuration for PortFast and BPDU Guard

Global configuration simplifies large-scale deployment:
```
spanning-tree portfast default
spanning-tree portfast bpduguard default
```

Logic:
- PortFast applies to **access ports** by default.
- BPDU Guard automatically applies to **PortFast-enabled ports**.

---

### BPDU Filter

BPDU Filter prevents a port from sending or receiving BPDUs, either conditionally or entirely, in order to control STP participation on specific ports.

#### Conditional BPDU Filtering (Global)

Configuration: `spanning-tree portfast bpdufilter default`

- **Trigger**: Applied automatically on ports configured with PortFast, unless manually disabled.
- **Action**: BPDUs are filtered (not sent or received) on the PortFast-enabled port. If a BPDU is received, BPDU filtering is automatically disabled on that port and normal STP operation resumes.
- **Recovery**: Automatic. The port resumes normal STP behavior if BPDUs are detected.
- **Scope**: Global — affects all PortFast-enabled ports.

#### Disabling STP on a Port (Interface-Level)

Configuration: `spanning-tree bpdufilter enable`

- **Trigger**: Manually applied to a specific interface.
- **Action**: The port stops sending and receiving all BPDUs, effectively disabling STP participation on that interface.
- **Recovery**: Only manual — BPDU filtering remains active until the command is removed.
- **Scope**: Interface-specific.

---

### Root Guard

**Root Guard** protects the stability of the spanning tree by preventing a port from becoming the root port if it receives superior BPDUs from another device.

Configuration: `spanning-tree guard root`

- **Trigger**: Detection of a superior BPDU.
- **Action**: The port enters a root-inconsistent (blocked) state for that VLAN.
- **Recovery**: The port automatically recovers when superior BPDUs stop arriving.

There is no global Root Guard command — it must be applied per interface.

---

### Loop Guard

Loop Guard prevents forwarding loops caused by unidirectional links on STP-enabled ports, helping maintain the stability of the spanning tree.

#### Enabling Loop Guard Per-Interface

Configuration: `spanning-tree guard loop`

- **Trigger**: Applied manually to a specific interface.
- **Action**: The port monitors BPDUs on a point-to-point link. If BPDUs stop arriving unexpectedly, the port is placed in a loop-inconsistent (blocked) state to prevent a loop.
- **Recovery**: Automatic. The port resumes normal STP operation once BPDUs are received again.
- **Scope**: Interface-specific.

#### Enabling Loop Guard Globally

Configuration: `spanning-tree loopguard default`

- **Trigger**: Applied globally on all point-to-point interfaces.
- **Action**: Automatically enables Loop Guard on all eligible interfaces to protect against unidirectional link failures.
- **Recovery**: Automatic on each interface when BPDUs are restored.
- **Scope**: Global — affects all point-to-point interfaces.

## Configuring Layer 2 EtherChannel

EtherChannel groups multiple physical interfaces into one logical channel, increasing bandwidth and redundancy while appearing as a single interface to STP.

---

### Manual EtherChannel Configuration

Each interface must be assigned to a channel group:
```
interface range g0/1 - 2
channel-group <number> mode on
```
Ensure that all commands on the same switch share the same number, although the channel-group number on the connected switch may vary.

Use these commands to verify:
```
show etherchannel   # configuration information
show etherchannel summary   # status information
show interfaces port-channel <number> # shows interface information
```

Note: “EtherChannel,” “PortChannel,” and “Channel Group” are synonymous in Cisco IOS.

---

### Dynamic EtherChannel Configuration

Dynamic negotiation protocols automate EtherChannel formation:
| Protocol | Type              | Command Mode         | Description                       |
| -------- | ----------------- | -------------------- | --------------------------------- |
| **PAgP** (Port Aggregation Protocol)| Cisco proprietary | `desirable` / `auto` | Negotiates EtherChannel formation |
| **LACP** (Link Aggregation Control Protocol)| IEEE 802.3ad      | `active` / `passive` | Industry-standard protocol        |

Examples:
```
channel-group <number> mode desirable   # PAgP
channel-group <number> mode active      # LACP
```

At least one side must use the “active” or “desirable” mode for negotiation to succeed.
The “on” mode bypasses both protocols and requires manual configuration on both sides.

---

### EtherChannel Consistency Checks

Before a port can join an EtherChannel, IOS verifies that its configuration matches existing members. Parameters checked include:
- Speed and duplex
- Access or trunk mode
- Access VLAN (for access ports)
- Allowed VLAN list (for trunk ports)
- Native VLAN (for trunk ports)

Ports with mismatched settings are excluded until configuration is consistent.

### EtherChannel Cost and Load Balancing
STP treats an EtherChannel as a single logical interface and adjusts its cost based on the number of active links:
| Configuration                    | Default Cost |
| -------------------------------- | ------------ |
| One active 1 Gbps link           | 4            |
| Two to eight active 1 Gbps links | 3            |
| Single 10 Gbps link              | 2            |

EtherChannel balances traffic using various load-balancing algorithms based on header information:
| Method         | Uses                            | OSI Layer |
| -------------- | ------------------------------- | --------- |
| `src-mac`      | Source MAC address              | 2         |
| `dst-mac`      | Destination MAC address         | 2         |
| `src-dst-mac`  | Both source & destination MAC   | 2         |
| `src-ip`       | Source IP address               | 3         |
| `dst-ip`       | Destination IP address          | 3         |
| `src-dst-ip`   | Both source & destination IP    | 3         |
| `src-port`     | Source TCP/UDP port             | 4         |
| `dst-port`     | Destination TCP/UDP port        | 4         |
| `src-dst-port` | Both source & destination ports | 4         |

Set the method globally: `port-channel load-balance <method>`

Goals of Load Balancing:
- Keep traffic from the same flow on a single physical link.
- Utilize all available links efficiently.
- Adjust dynamically as links fail or recover.
- Maintain forwarding performance at hardware speed.
