## TCP/IP Layer 4 Protocols: TCP and UDP

At the **Transport Layer** of the TCP/IP model, two key protocols—**Transmission Control Protocol (TCP)** and **User Datagram Protocol (UDP)**—manage the flow of data between applications on different devices.  

| Function | Description |
|-----------|--------------|
| **Multiplexing using ports** | Enables the receiving host to direct incoming data to the correct application using port numbers. |
| **Error recovery (reliability)** | Uses sequence and acknowledgment fields to track data and ensure successful delivery. |
| **Flow control using windowing** | Prevents buffer overflow by managing how much data can be sent at a time. |
| **Connection establishment and termination** | Sets up and ends sessions, initializing port numbers and sequence information. |
| **Ordered data transfer and segmentation** | Breaks data into segments for transmission and ensures reassembly in the correct order. |

> UDP supports only **port multiplexing**, while **TCP** supports all the features listed above.

---

## Transmission Control Protocol (TCP)

Applications choose **TCP or UDP** depending on their need for reliability and performance.  
TCP provides dependable data delivery through various mechanisms that function identically whether two hosts are on the same LAN or across the Internet.

The message that begins with a **TCP header**, followed by application data, is called a **TCP segment**.

### Multiplexing Using TCP Port Numbers

**Multiplexing** ensures data is sent to the right application. TCP and UDP use **port numbers** within their headers for this purpose.

Each connection is identified by a **socket**, composed of:
- An IP address  
- A transport protocol (TCP/UDP)  
- A port number  

**Port ranges defined by IANA:**
- **Well-Known Ports (0–1023):** Reserved for standard services (e.g., HTTP, FTP).  
- **Registered Ports (1024–49151):** Used by user applications or registered services.  
- **Dynamic or Private Ports (49152–65535):** Temporarily assigned for client connections.  

A unique socket combination identifies every connection, ensuring data is properly delivered to the corresponding application.

### TCP Connection Establishment and Termination

Before data transfer can occur, TCP must establish a **connection** using the **three-way handshake**:

1. **SYN** – Client → Server  
2. **SYN, ACK** – Server → Client  
3. **ACK** – Client → Server  

To close a session, TCP uses a **four-step termination** process:

1. **FIN, ACK** – Client → Server  
2. **ACK** – Server → Client  
3. **FIN, ACK** – Server → Client  
4. **ACK** – Client → Server  

**Connection-oriented protocol:** Requires setup before transmission.  
**Connectionless protocol:** Sends data without prior setup (e.g., UDP).

---

### Error Recovery and Reliability

TCP assigns **sequence numbers** to bytes of data and uses **acknowledgments** to confirm successful delivery.  
If data is lost or corrupted, the receiving host requests retransmission, ensuring complete and accurate delivery.

---

### Flow Control Using Windowing

The **window size** determines how much data can be sent before requiring acknowledgment.  
This sliding window mechanism allows the receiver to control transmission speed dynamically—speeding up or slowing down data flow as needed to avoid congestion.

---

## User Datagram Protocol (UDP)

Unlike TCP, **UDP** is **connectionless** and does not provide:
- Reliability  
- Flow control  
- Ordering  
- Segmentation management  

However, it still enables **data transfer and multiplexing** using port numbers, but with minimal overhead—its header is only **8 bytes**, compared to TCP’s **20 bytes**.  

UDP is ideal for applications where speed matters more than reliability (e.g., streaming, DNS, VoIP).

## TCP/IP Applications

### Web Browsing with HTTP

Web browsing relies on the **Hypertext Transfer Protocol (HTTP)** at the application layer.  
Let’s explore how browsers locate and retrieve web content using HTTP and DNS.

---

### Uniform Resource Identifiers (URIs)

A **Uniform Resource Identifier (URI)** identifies a specific resource, such as a web page.  
It consists of three main components:
1. **Scheme** – The protocol (e.g., `http`, `https`)  
2. **Authority** – The domain name or IP address  
3. **Path** – The resource location on the server  

For example, in `https://example.com/index.html`:
- `https` is the scheme  
- `example.com` is the authority  
- `/index.html` is the path  

While many people use the term **URL**, *URI* is the more accurate and general term.

---

### Resolving Web Server Addresses with DNS

Before a browser can communicate with a server, it must convert the domain name into an IP address using the **Domain Name System (DNS)**.

#### Basic DNS Resolution
1. The user enters a URI in the browser.  
2. The client sends a DNS query (UDP, port 53) to the DNS server, often learned through DHCP.  
3. The DNS server replies with the IP address.  
4. The client uses that IP to initiate a TCP connection to the web server.

#### Recursive DNS Lookup
If the enterprise DNS server doesn’t know the answer:
1. It queries a **root DNS server**.  
2. The root server responds with a **top-level domain (TLD)** DNS address (e.g., for `.com`).  
3. The TLD server replies with the address of the **authoritative DNS** for the domain.  
4. The authoritative server provides the final IP address.  
5. The enterprise DNS sends the resolved IP back to the client.  

Both clients and servers can **cache** DNS results to reduce lookup times for future requests.

---

### Transferring Files with HTTP

HTTP defines how files (like web pages, images, and scripts) are transferred between a **client** and a **server**.

- A **client** sends an **HTTP GET request**, asking for a specific resource.  
- The **server** responds with an **HTTP response**, typically including:
  - A **status code** (e.g., `200 OK`)  
  - The requested file contents

## HTTP Versions Overview

### HTTP 1.0 and 1.1
These early versions (from the 1990s) use TCP—typically over **port 80**—and rely on simple **GET** requests and responses.  
They do not use encryption and maintain backward compatibility, which is why version differences had minimal impact on network behavior.

### HTTP/2 and TLS
To secure communication, **Transport Layer Security (TLS)** introduced **HTTPS**, running over **TCP port 443**.  
TLS provides:
- Encryption  
- Authentication  
- Data integrity  

**HTTP/2**, released in the mid-2010s, optimized performance through multiplexing and header compression without changing ports or URLs.

### HTTP/3 and QUIC
**HTTP/3** replaces TCP with **QUIC**, a transport protocol built on **UDP (port 443)**.  
QUIC integrates TLS for encryption and reduces latency by streamlining the connection process.  
Standardized in **RFC 9114 (2022)**, HTTP/3 has rapidly gained adoption across major platforms.  

From a networking perspective, HTTP/3 introduces new packet structures and behaviors that affect traffic inspection and filtering.
