## SDN (Software-Defined Networking) and Controller-Based Networking

Modern networking tasks can be grouped into logical “planes.” This chapter revisits familiar networking behaviors from a programmability perspective and organizes them into three major planes.

---

## The Data Plane

The **data plane** refers to everything a device does to *receive*, *process*, and *forward* packets. This includes:

- Inspecting incoming frames or packets  
- Making forwarding decisions  
- Delivering traffic out the appropriate interface  

Because its primary job is forwarding traffic, the data plane is often called the *forwarding plane*.

---

## The Control Plane

The **control plane** consists of all functions that shape the behavior of the data plane. Most of these functions build and update the tables consumed by the data plane—such as routing tables, MAC address tables, and more.

In traditional networks:

- Every device maintains its own distributed control plane.
- Routing protocols and learned information exist independently on each node.
- Each device uses its local control plane to populate its own data plane tables.

The data plane depends entirely on the information prepared and maintained by the control plane.

---

## The Management Plane

The **management plane** handles tasks that relate to managing devices rather than directly influencing how packets are forwarded. Protocols such as **Telnet** and **SSH** live in this plane. While the control plane impacts forwarding behavior, the management plane provides operational access without interacting directly with forwarding logic.

---

## Cisco Switch Data-Plane Internals

On switches, forwarding logic typically runs in specialized hardware rather than on the CPU:

- **ASICs** (Application-Specific Integrated Circuits) perform high-speed forwarding.
- **TCAM** (Ternary Content-Addressable Memory) stores tables such as MAC entries or ACLs and enables extremely fast lookups.

TCAM allows an ASIC to match specific fields—like a MAC address—without looping through a list. Instead, the table returns the match instantly.

Most control and management plane functions run in **Cisco IOS**, while the data plane and MAC-learning functions run in hardware (ASICs). Routers and switches use similar concepts: ASIC-based forwarding and hardware-accelerated lookup tables.

## Controllers and Software-Defined Architecture

### Centralized Controllers

Traditional networks use a **distributed control plane**, meaning each device runs its own control processes and exchanges information with neighboring devices.

A centralized model—where one server or system holds all control logic—could also work. Although historically networking developed around distributed control, modern SDN architectures often leverage centralization because:

- Centralized applications are easier to develop and maintain.
- All network data is available in one place.
- Automation becomes much more scalable.

A **controller** (or SDN controller) centralizes awareness and, in many designs, control of network devices. Depending on the architecture, the controller may:

- Fully replace the distributed control plane  
- Operate alongside traditional control mechanisms  
- Observe device behavior without overriding it  

---

## The Southbound Interface (SBI)

In SDN diagrams, network devices typically appear *below* the controller. The interface that connects the controller to these devices is the **southbound interface (SBI)**.

Key characteristics:

- SBIs include both *protocols* and *APIs*.  
- They enable the controller to communicate with device software.  
- One major goal is to let the controller program the device’s data-plane forwarding tables.  

The SBI represents the communication bridge between the controller software and the control or data-plane elements on the devices.

---

## The Northbound Interface (NBI)

Controllers collect and store large amounts of network information. The **northbound interface (NBI)** exposes this information so that applications—running either on the same server or remote systems—can:

- Retrieve network state  
- Push configuration intent  
- Program flows using the controller’s SBI  

RESTful APIs using **HTTP**, with data in **JSON** or **XML**, are commonly used for NBIs in modern SDN architectures.

## Examples of Network Programmability and SDN

---

### OpenDaylight and OpenFlow

The Open Networking Foundation (ONF) promotes an SDN model centered around **OpenFlow**. OpenFlow:

- Defines a consistent structure for how switches process traffic using ASICs and TCAM.  
- Lets switches operate flexibly as L2, L3, or more advanced forwarding devices.  
- Uses a controller-driven architecture where applications program flows through NBIs, while OpenFlow acts as the SBI.

In this model, the controller—such as **OpenDaylight**—has a significant role in network operations.

---

### Cisco Application Centric Infrastructure (ACI)

Cisco ACI was built with applications as its foundation. Instead of configuring the network first and placing apps on top, ACI asks: *What do the applications need?*

#### ACI’s Physical Spine-Leaf Design

ACI relies on a predictable and scalable topology:

- Every **leaf** switch connects to every **spine** switch.  
- Leaves do **not** connect to other leaves.  
- Spines do **not** connect to other spines.  
- Endpoints (servers, VMs, containers) attach only to leaf switches.  

#### Intent-Based Networking with APIC

ACI uses **intent-based networking (IBN)**. Engineers define *what should happen*, and the system determines *how* to implement it. ACI uses:

- **Endpoints** (VMs, servers, containers)  
- **Policies** describing allowed communication  
- The **Application Policy Infrastructure Controller (APIC)**, which translates intent into device configuration  

With ACI, engineers no longer configure VLANs, trunks, ACLs, and other low-level details directly; APIC does it for them.

---

## Summary: OpenFlow vs Cisco ACI

| Criteria | OpenFlow | ACI |
|---------|----------|-----|
| Changes traditional device control plane | Yes | Yes |
| Provides a centralized control point | Yes | Yes |
| Level of centralization | High | Partial |
| SBI protocol | OpenFlow | OpFlex |
| Controllers referenced | OpenDaylight | APIC |
| Defining organization | ONF | Cisco |

## Comparing Traditional and Controller-Based Networks

Network management typically falls into two categories:

- **Configuration management**: commands and settings applied to devices  
- **Operational management**: monitoring, telemetry, reporting, and alerting  

---

## How Automation Changes Network Management

Controllers define consistent **data models** for configuration and operational details. Instead of parsing CLI output (as older scripts often had to do), automation tools can:

- Query structured data through NBIs  
- Use model-driven information  
- Apply analytics to large datasets  
- Perform actions consistently and quickly  

Some key advantages:

- APIs simplify automation compared to traditional manual configuration  
- Centralized operational data enables powerful analytics  
- Automation reduces errors and speeds up deployments  
- New models account for external context such as time, load, or business requirements  

---

## Traditional Networks vs Controller-Based Networks

By centralizing many functions, controllers reshape how networks operate:

- Engineers focus on intent, not per-device commands  
- Devices receive consistent configurations  
- SBIs push configuration automatically  
- NBIs allow external applications to influence the network  
- Networks become more predictable, scalable, and easier to troubleshoot  

Controller-based models support DevOps workflows and automated pipelines that treat the network as a programmable system rather than a series of isolated devices.
