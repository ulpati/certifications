# CHAPTER 51 - Cisco Software-Defined Access
**Rewritten and reformatted for educational use**  
**Source: *CCNA 200-301 Volume 2* by Wendell Odom**

Cisco Software-Defined Access (SD-Access) introduces a modern, software-driven approach to designing campus networks. Instead of relying solely on traditional distributed configuration, SD-Access uses controllers—primarily Cisco Catalyst Center—along with APIs to automate and orchestrate the entire network fabric.

---

## Cisco SD-Access Fabric, Underlay, and Overlay

In SD-Access, the controller’s southbound layer interacts with three fundamental components: the **underlay**, the **overlay**, and the **fabric**.

### **Underlay**
The underlay consists of the physical network infrastructure—switches, routers, wired and wireless links—that ensures IP reachability between all SD-Access nodes. Its main purpose is to support the dynamic creation of VXLAN tunnels used by the overlay.

### **Overlay**
The overlay is formed by VXLAN tunnels established between SD-Access devices, including switches and fabric-enabled APs. These tunnels carry user traffic across the fabric independently of traditional Layer 2 and Layer 3 forwarding mechanisms.

### **Fabric**
The fabric is the combination of both underlay and overlay elements. A single network may include one or several fabrics, each providing a consistent method for forwarding traffic across the SD-Access domain.

Within this architecture, endpoint traffic travels through VXLAN tunnels in the overlay. This process bypasses traditional switching and routing behavior, and thanks to hardware acceleration in the switch ASICs, there's no performance degradation.

---

## Cisco SD-Access Underlay

The underlay provides the IP connectivity required for fabric edge nodes to build VXLAN tunnels in the overlay. It includes all the hardware, cabling, wireless links, and the configuration needed to support the fabric.

### **Using Existing Hardware**

Organizations can often convert their current campus switches into an SD-Access underlay—provided the equipment is listed as compatible and supports the required software levels. However, deploying SD-Access on live production hardware carries some risks:

- Cisco Catalyst Center should not automatically configure the underlay if devices are actively serving production traffic.
- Existing devices must be validated against SD-Access compatibility requirements.
- Software versions must meet role-specific minimums.

Before deploying the fabric, each device must be assigned a specific role:

- **Fabric Edge Node:** Connects to endpoint devices (similar to access or leaf switches).  
- **Fabric Border Node:** Connects to networks outside SD-Access, such as WAN routers or data centers.  
- **Fabric Control-Plane Node:** Handles LISP control-plane operations and requires more CPU and memory.

### **Using New Hardware**

Deploying a greenfield SD-Access fabric eliminates many compatibility concerns. With fully supported switches and software, Cisco Catalyst Center can automatically configure the underlay.

A key design model here is the **routed access layer**, where:

- All switches operate as Layer 3 devices.
- All inter-switch links run as Layer 3, removing the need for STP.
- IS-IS is the default routing protocol.
- Fabric edge nodes serve as the default gateways for endpoints.
- FHRPs such as HSRP are no longer necessary because gateway responsibilities shift to the fabric edge.

## Cisco SD-Access Overlay

When an endpoint sends traffic, the first fabric edge node encapsulates the frame inside a VXLAN header and forwards it into the fabric. Other nodes route the packet based on VXLAN tunnel identifiers. On reaching the destination fabric edge node, the VXLAN header is removed and the original frame is delivered to the endpoint. All encapsulation/decapsulation is hardware-accelerated.

### **VXLAN Tunnels (Data Plane)**

VXLAN in SD-Access must:

- Be handled entirely by switch ASICs to maintain performance.
- Support extensible headers required by SD-Access features.
- Encapsulate full Layer 2 frames (not just IP packets) to preserve both L2 and L3 forwarding behavior.

The underlay uses a dedicated IP address space that differs from the enterprise address space used by endpoints and overlay tunnels.

### **LISP for Overlay Control-Plane**

Traditional MAC learning (L2) and IP route learning (L3) do not operate the same way in SD-Access. Instead, the fabric uses **LISP (Locator/ID Separation Protocol)** for endpoint discovery and mapping.

The general behavior is:

1. Fabric edge nodes learn endpoint information (MAC, IP, and subnet) using standard methods. Each endpoint is identified with an Endpoint Identifier (EID).
2. Edge nodes register reachable EIDs to the LISP map server.
3. The LISP map server maintains EID-to-RLOC (Routing Locator) mappings, showing which fabric node can reach each endpoint.
4. When forwarding traffic, fabric devices query the LISP map server to find the correct RLOC.

This architecture shifts identity from IP address–based identification to **user or device identity**, simplifying policy enforcement and mobility.

## Cisco Catalyst Center and SD-Access Operation

Cisco Catalyst Center serves two major purposes:

- Acts as the controller for SD-Access fabrics.
- Provides a full-featured network management platform for traditional environments.

### **Southbound and Northbound APIs**

- **Northbound:** REST APIs for external automation and integration.
- **Southbound:**  
  - Traditional protocols: Telnet, SSH, SNMP  
  - Modern protocols: NETCONF, RESTCONF

## Cisco Catalyst Center and Scalable Groups

### **Limitations of Traditional ACL Security**

IP-based access lists suffer from:

- Difficulty removing ACEs without breaking old logic.
- Increasing complexity as ACLs grow.
- Challenging end-to-end troubleshooting.

### **Group-Based Security in SD-Access**

SD-Access resolves these challenges using **scalable groups**:

- Users and devices are assigned to groups.
- Each group receives a **Scalable Group Tag (SGT)**.
- A matrix defines which SGTs may communicate with others.
- Policies remain separate, easy to document, and easy to remove.

When an endpoint sends its first packet:

1. The fabric edge node contacts Cisco Catalyst Center.
2. Catalyst Center identifies the user/device and assigns an SGT.
3. Catalyst Center checks whether communication is allowed between the source and destination SGTs.
4. If allowed, the controller orchestrates the appropriate VXLAN tunnel. Otherwise, traffic is denied.

## Cisco Catalyst Center as a Network Management Platform

Cisco Catalyst Center supports features commonly found in enterprise NMS platforms:

- Centralized (“single-pane-of-glass”) management
- Device discovery, inventory, and topology mapping
- Support for LAN, WAN, and data center operations
- Use of SNMP, SSH, Telnet, CDP, and LLDP
- Lifecycle management workflows
- QoS deployment and application visibility
- Converged wired/wireless management
- SWIM for image automation
- Plug-and-Play for onboarding new devices

### **Unique Capabilities**

- **Application Policy:** Simple QoS deployment through templates.  
- **Encrypted Traffic Analytics (ETA):** Detects threats in encrypted traffic.  
- **Device 360 and Client 360:** Detailed health and performance insights.  
- **Network Time Travel:** Historical client performance visualization.  
- **Path Trace:** End-to-end packet-path analysis.

## Artificial Intelligence (AI), Machine Learning (ML), and Operations Management

### **Artificial Intelligence**

AI refers to systems capable of performing tasks traditionally requiring human intelligence. Two major forms include:

- **Narrow AI:** Designed for specific tasks such as speech recognition, image analysis, or virtual assistants.
- **Generative AI:** Can learn, be trained, and produce results based on patterns and context, more closely resembling human reasoning.

### **Machine Learning**

A subset of AI focused on developing algorithms and models that learn from data. ML systems improve automatically as more data is collected, making them useful for predictions and automated decision-making.

**Predictive AI** goes a step further by anticipating user intent with minimal input.

### **AI for IT Operations (AIOps)**

AIOps applies AI/ML to streamline and automate IT operations. Common use cases include:

- Automation of repetitive tasks  
- Real-time monitoring and analytics  
- Predictive issue detection  
- Improved collaboration and shared troubleshooting  
- Root cause analysis through deep infrastructure visibility
