# CHAPTER 53 - Understanding Ansible and Terraform
> **Source: _CCNA 200-301 Volume 2_ by Wendell Odom**

In modern networks, configuration consistency is essential. As infrastructures grow, relying on manual device configuration becomes increasingly inefficient and error-prone. This chapter explores key challenges in configuration management and introduces two popular automation tools—**Ansible** and **Terraform**—that help engineers deploy, manage, and maintain network environments more reliably.

---

## Device Configuration Challenges and Solutions

### Configuration Drift

When network devices are configured manually, “configuration drift” becomes almost unavoidable. Drift occurs when device settings gradually diverge from the intended baseline configuration. This happens because:

- Devices do not inherently keep a detailed historical record of configuration changes—what was modified, by whom, or when.
- External systems such as ticketing or change-management tools may store partial information, but they rely heavily on consistent human input and cross-referencing.
- Over long periods and multiple changes, retrieving accurate historical configuration data becomes difficult and time-consuming.

### Centralized Configuration Files and Version Control

A practical first step to control drift is **centralizing configuration files**. Many organizations copy device configurations into a shared repository for backup and team access.

When paired with **version control**, this approach becomes significantly more effective. Version control tools can:

- Track exactly what changed in each file.
- Record who made the modifications and when.
- Compare versions over time to understand how the configuration evolved.

### Configuration Monitoring and Enforcement

Automation tools allow engineers to modify device configurations by updating the corresponding files in a central repository. The tool then pushes these changes to the devices. After deployment, the system can verify that the device configuration matches the intended configuration.

Some drift may still occur due to manual edits on the devices themselves. To address this, configuration management tools can:

- Continuously monitor active device configurations.
- Detect mismatches between the actual and expected configurations.
- Automatically correct deviations or alert network engineers.

This capability may be labeled *configuration monitoring* or *configuration enforcement*, depending on whether the system auto-corrects problems or provides notifications.

### Configuration Provisioning

Configuration provisioning describes how changes stored in the repository are ultimately applied to devices. Common features in provisioning tools include:

- Applying updated configuration files to one or more devices.
- Targeting specific groups of devices based on attributes such as device role.
- Detecting whether configuration commands are accepted or rejected.
- Automatically rolling back changes if any errors occur.
- Performing a "dry run" to validate proposed changes before applying them.
- Verifying that device configurations match the intended state once updates are applied.
- Deciding whether or not to save changes to startup-config.
- Using templates and variables to standardize configurations across similar devices.
- Scheduling automated tasks without requiring engineers to be present.

#### Configuration Templates and Variables

Automation tools separate a device’s configuration into:

- **Templates**, which contain settings shared across all devices of a given role.
- **Variables**, which store device-specific details.

Although this may seem like additional work, templates offer several advantages:

- They enforce standardized configurations, preventing one-off “snowflake” devices.
- New devices can be deployed faster by copying an existing variable file and adjusting values.
- Troubleshooting becomes easier since resolving an issue in the template fixes it across all devices using that template.
- Version tracking is simplified because engineers can quickly identify whether an issue stems from a template change or a variable change.

#### Files That Control Configuration Automation

Automation systems use various types of files—some for logic, some for device details, and some for templates. These files direct the automation tools on what tasks to perform, when to perform them, and how to interact with devices or external systems. Many tools also support extensions using general-purpose programming languages.

## Ansible and Terraform Basics

### Ansible

After installing Ansible, you typically work with a set of text-based files—many written in **YAML**:

- **Playbooks** define tasks and logic Ansible should execute.
- **Inventory files** list devices along with details such as roles or grouping attributes.
- **Templates** (written using Jinja2) represent device configurations with placeholders for variables.
- **Variable files** define the values Ansible inserts into templates.

Ansible is **agentless**, meaning it does not require custom software installed on the device. Instead, it leverages built-in capabilities such as **SSH** and **NETCONF** to gather information and apply configuration changes.

By default, Ansible uses a **push model**, where the control node sends configuration to devices. A pull model is also possible using **Ansible-pull**, where devices retrieve their configurations from a central source.

Ansible excels at **configuration provisioning**, but it can also perform configuration monitoring using specialized modules that detect differences between expected and actual device states.

### Terraform

Terraform is an **Infrastructure as Code (IaC)** tool often used to deploy both cloud and on-premises resources. Its core components include:

- **Configuration files** describing the desired infrastructure.
- **Providers**, which act as plugins for platforms like AWS, Azure, and Google Cloud.
- **Resources** representing infrastructure elements such as VMs, networks, or databases.
- **Data sources** for referencing existing infrastructure inside a configuration.
- **Variables** to make configurations reusable.
- **State files**, which track the current state of the deployed infrastructure.
- **Modules**, which group related resources into reusable, modular components.

Terraform interacts with external systems through their APIs and uses **HashiCorp Configuration Language (HCL)** for its configuration files.

Its workflow consists of three clear stages:

1. **Write** — Define desired infrastructure resources.  
2. **Plan** — Generate an execution plan showing what will be created, updated, or removed.  
3. **Apply** — Execute the plan and deploy the infrastructure in the correct order.

While Ansible focuses on configuring devices, Terraform is generally used for provisioning infrastructure itself.

## Summary of Configuration Management Tools

| Attribute | Ansible | Terraform |
|----------|---------|-----------|
| File type for actions or config | Playbook | Configuration |
| Protocol used with network devices | SSH, NETCONF | APIs |
| Execution mode | Push (default), Pull via Ansible-pull | Push |
| Modeling language | YAML | HashiCorp Configuration Language (HCL) |
